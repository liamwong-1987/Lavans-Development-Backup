# Canvas AGENT：可审核交付架构与第一阶段执行底座设计

最后更新：2026-08-20（Asia/Shanghai）

## 1. 目标

把 Lavans 画布 AGENT 从“一次启动后自动跑到成片”调整为“用户一句话启动、低风险步骤自动完成、关键质量关卡强制审核、高成本步骤精确授权”的可控制作系统。

本设计同时解决两个问题：

1. 剧本、分镜、角色、场景、旁白、图片和视频任何一项不满意时，用户可以修改、派生版本和只重做受影响部分，不会自动扩大错误并造成 API 费用损失。
2. 上下文压缩、换窗口、服务重启或开发中断后，Codex 能从统一任务账本和代码证据恢复，继续完成画布 AGENT 的全部交付。

## 2. 已确认的产品决定

1. 不做“一键直接成片”。一句话只负责启动完整工作流。
2. 采用“关键阶段人工确认、阶段内部低风险步骤自动执行”的 B 模式。
3. 采用“画布审核节点 + 右侧专业审核栏”的 B 界面。
4. 用户修改上游后，采用 A 规则：保留全部下游成果，准确标记受影响和已过期状态，禁止误用，由用户选择重做范围。
5. 采用独立的“版本依赖与审核引擎”，不把审核规则零散堆入现有阶段代码。
6. 原 16 个技术阶段重组为 10 个交付阶段。
7. 画布 AGENT 与一键复色始终是两套完全独立的软件，不共享素材、模板、任务、设置、Provider 或模型选择。
8. Lavans 开发只使用 GPT/Codex；画布 AGENT 运行时使用画布 API 设置中用户当前配置和授权的模型。

## 3. 10 个交付阶段

| 阶段 | 名称 | 核心产出 | 强制审核出口 |
|---:|---|---|---|
| 1 | 执行底座与恢复账本 | 版本依赖、审核引擎、影响传播、费用安全门、统一任务账本、新窗口恢复 | 底座测试与恢复演练通过 |
| 2 | 产品事实与调研 | 资料、证据等级、事实锁、禁说项、离线故事检索和创意研究 | 用户确认产品事实与调研边界 |
| 3 | 创意与剧本锁定 | 创意方向、完整剧本、版本对比、局部修改和唯一锁定版本 | 用户锁定剧本版本 |
| 4 | 结构化分镜与资产台账 | 逐镜脚本、角色、产品、场景、道具、Logo 和镜头引用 | 用户锁定分镜脚本与资产需求 |
| 5 | 模型策略与费用防线 | 图片/视频 Provider、能力、比例、模式、预算、备用和重试策略 | 用户批准生成方案和费用上限 |
| 6 | 视觉资产生产 | 角色锚点、产品保真图、场景、道具及版本 | 用户锁定视觉资产版本 |
| 7 | 分镜图、故事板与调度 | 逐镜画面、首尾帧、故事板、机位、站位和运动路线 | 用户锁定画面与调度 |
| 8 | 声音与逐镜制作包 | 旁白、对白、音色、语速、字幕、音乐、音效和逐镜视频提示词 | 用户锁定声音和提示词 |
| 9 | 逐镜视频生产与验收 | 低成本样片、逐镜视频、失败重试和逐镜锁定 | 每个镜头验收；批量付费前再次确认 |
| 10 | 合成、质检与最终交付 | 剪辑、转场、声音、字幕、成片、制作包及稳定性验收 | 用户最终验收成片和制作包 |

阶段内部继续使用固定 Task ID。阶段数量减少不代表功能减少，而是按用户审核边界合并相关工作。

## 4. 既有成果映射

- 已完成的 Skill 卡片、问卷、资料上传、Run/Stage/Artifact、暂停/恢复/取消和项目初始化，映射到阶段 1–2。
- 已完成的故事库阻塞、离线检索、创意方向、最终剧本和防复刻流程，映射到阶段 2–3。
- 已完成的剧本不可变版本、手动/AI 修订、批准和锁定，映射到阶段 3。
- 新阶段 1 不重做上述功能；它为这些成果补齐统一版本依赖、审核关卡、影响传播和恢复账本，再把后续阶段建立在该底座上。

## 5. 系统架构

### 5.1 模块边界

新增逻辑拆成独立模块，避免继续扩大现有 2.2 万行画布主文件和 5000 行后端主路由：

- `Artifact Version Store`：创建、读取和验证不可变产物版本。
- `Dependency Graph`：记录产物版本之间的输入依赖和下游引用。
- `Approval Gate Engine`：管理审核、批准、锁定、过期和复核状态。
- `Impact Propagator`：上游改变时计算真正受影响的下游节点。
- `Execution Guard`：在执行和付费调用前检查锁定状态、过期状态、预算和授权。
- `Task Ledger`：持久化总阶段、Task、用户决定、证据、测试和下一步。
- `Recovery Auditor`：在启动、新窗口和服务重启时核对账本、Run、版本文件和画布节点。
- `Canvas Projection`：把后端事实状态投影为画布节点和右侧审核栏，不把前端临时状态当作事实来源。

### 5.2 事实来源

- 不可变产物文件和元数据是内容事实来源。
- Dependency Graph 是版本依赖事实来源。
- Task Ledger 是开发与交付进度事实来源。
- 后端 Run 是当前运行状态事实来源。
- 画布节点是上述状态的可见投影，可以从后端重建。

## 6. 统一产物版本模型

所有可审核产物使用同一基础结构：

```json
{
  "artifactVersionId": "storyboard-shot-005-v003",
  "artifactType": "storyboard-shot",
  "logicalArtifactId": "storyboard-shot-005",
  "version": 3,
  "source": "ai-generation",
  "contentPath": "storyboard/shot-005/v003.png",
  "metadataPath": "storyboard/shot-005/v003.json",
  "contentHash": "sha256",
  "inputRefs": [
    { "artifactVersionId": "script-v004", "role": "locked-script" },
    { "artifactVersionId": "shot-script-005-v002", "role": "shot-script" },
    { "artifactVersionId": "character-hero-v002", "role": "character-anchor" }
  ],
  "approvalState": "locked",
  "validityState": "current",
  "createdAt": 0,
  "approvedAt": 0,
  "lockedAt": 0
}
```

所有成功版本不可原地覆盖。失败、取消和中断是 Attempt，不占用成功版本。

## 7. 状态模型

### 7.1 审核状态

- `draft`
- `awaiting-review`
- `approved`
- `locked`
- `superseded`

### 7.2 有效性状态

- `current`：全部输入仍是当前有效版本。
- `needs-review`：上游变化，可能仍可复用，但必须人工确认。
- `stale`：明确基于旧输入，禁止进入后续执行。
- `invalid`：文件缺失、哈希不一致或依赖损坏。

审核状态与有效性状态分开。一个曾经 `locked` 的产物在上游变化后可以保留锁定历史，但有效性变为 `needs-review` 或 `stale`。

## 8. 影响传播规则

1. 创建新上游版本不会删除旧版本或任何下游文件。
2. 系统从被替换版本沿 Dependency Graph 向下遍历。
3. 直接引用旧版本的产物标记 `needs-review` 或 `stale`。
4. 受影响状态继续向下传播，但不影响没有依赖关系的其他镜头。
5. 用户可以：
   - 确认旧成果仍适用并重新绑定新输入；
   - 只重做受影响节点；
   - 创建分支版本；
   - 暂时保留状态，停止后续执行。
6. 自动确认只允许用于确定性的无内容变化迁移，例如哈希相同的输入重新登记；内容判断必须由用户确认。

## 9. 审核界面

采用“画布审核节点 + 右侧专业审核栏”：

- 画布节点显示流程位置、版本、状态灯、受影响数量、锁定与解锁关系。
- 右侧栏显示完整内容、版本对比、事实冲突、依赖、受影响下游、预计费用、手动修改、AI 勾选修改、批准和锁定。
- 用户能枚举的选择全部使用单选或多选；只有“其他”显示补充输入框。
- 未锁定的审核关卡让下游保持“未解锁”。
- 修改上游后，下游节点保留在原位置并显示黄色“需要复核”或红色“已过期”。

## 10. 执行与费用安全门

所有外部模型调用统一经过 Execution Guard：

1. 输入产物存在且哈希正确。
2. 所有必需输入是 `locked + current`，或拥有本次精确人工复用授权。
3. Provider、模型、能力、比例、时长和数量与当前设置匹配。
4. 显示预计调用数量、单价/估算费用、重试上限和备用 Provider。
5. 手动、半自动、自动模式均受项目预算和高价确认限制。
6. 已过期、需要复核或无依赖来源的输入禁止进入付费生成。
7. 授权精确绑定 Provider、模型、输入版本、数量、预算和操作 ID；任何一项变化后旧授权失效。

## 11. 统一任务账本

建立一个机器可读账本和一个人类可读进度页：

```text
docs/canvas-agent/
  execution-ledger.json
  recovery-protocol.md
  decisions.md
  phase-mapping.md
docs/Canvas-Agent开发进度.md
docs/Canvas-Agent开发任务总表.md
```

`execution-ledger.json` 至少包含：

- `schemaVersion`
- `planVersion`
- 10 个阶段及固定 Task ID
- 每个 Task 的 `pending / in-progress / blocked / tested / awaiting-user / accepted`
- 用户确认的决定及时间
- 修改文件和不可变证据
- 备份位置
- 测试命令、结果和时间
- 当前阻塞条件
- 唯一的 `nextAction`
- 最近一次代码和账本一致性检查

只有账本状态、测试证据和用户验收三者一致，Task 才能标记完成。

## 12. 上下文压缩与新窗口恢复协议

新窗口或上下文压缩后必须按固定顺序恢复：

1. 读取本设计、`execution-ledger.json`、任务总表和开发进度。
2. 检查 Git 工作区，不覆盖用户已有修改。
3. 验证账本中记录的关键文件、备份和测试证据仍存在。
4. 读取后端 Run 和画布记录，确认运行状态与账本一致。
5. 如果不一致，先运行 Recovery Auditor，生成差异报告，不直接继续执行。
6. 只从账本唯一 `nextAction` 对应的第一个未完成 Task 继续。
7. 已验收阶段不得重做；待用户验收时必须停止。
8. 缺少真实依赖、授权或付费确认时必须阻塞，不能伪造产物。

每完成一个 Task，原子更新账本；每完成一个阶段，更新任务总表、开发进度、测试证据和下一阶段入口。

## 13. 第一阶段 Task

|---:|---|---|
| 1.1 | 精确备份与代码基线 | 现有画布、配置、关键数据和测试基线有可校验备份 |
| 1.2 | 统一产物版本结构 | 模型、校验器和不可变存储测试通过 |
| 1.3 | 依赖关系图 | 输入引用、反向查询、循环拒绝和持久化测试通过 |
| 1.4 | 影响传播 | 只标记受影响节点，其他镜头保持有效，文件零删除 |
| 1.5 | 审核关卡引擎 | 审核、批准、锁定、替换、过期和复核状态机测试通过 |
| 1.6 | 付费步骤安全门 | 未锁定、过期、预算或授权不匹配时全部阻断 |
| 1.7 | 统一任务账本 | JSON Schema、原子写入、证据登记和单一下一步测试通过 |

## 14. 错误处理与恢复

- 原子写入：版本、依赖图和账本先写同目录临时文件，校验后原子替换。
- 幂等：写操作携带 operation ID，重复请求不产生重复版本或重复依赖。
- 哈希校验：内容文件和元数据不一致时标记 `invalid`，禁止执行。
- 部分失败：保留已完成产物和 Attempt，重试只执行失败 Task 或镜头。
- 服务重启：运行中任务恢复为 `interrupted`；不自动重复付费调用。
- 账本损坏：从备份和代码证据生成恢复报告，需确认后修复。
- 影响传播中断：使用传播操作 ID 重放，结果必须幂等。
- 前端刷新：从后端事实状态重建节点，禁止用浏览器临时状态覆盖后端。

## 15. 测试策略

第一阶段采用测试先行。至少覆盖：

1. 不可变版本不能覆盖，哈希异常被阻断。
2. 依赖关系可正向和反向查询，循环依赖被拒绝。
3. 剧本单镜头变化只影响相关分镜、图片、旁白和视频。
4. 未受影响镜头继续保持 `current`。
5. 已付费生成文件在传播和取消过程中零删除。
6. 用户确认旧成果可复用后，重新绑定新输入并保留审计记录。
7. `needs-review / stale / invalid` 输入无法进入付费任务。
8. Provider、模型、输入版本、数量或预算变化使旧授权失效。
9. 账本只能存在一个合法 `nextAction`，非法状态拒绝保存。
10. 上下文恢复按照账本继续，不重做已验收 Task。
11. 服务重启恢复运行状态，不重复外部调用。
12. 画布节点从后端状态重建，显示审核和过期状态。
13. 当前阶段 2 的 23 项测试保持通过。
14. 生产画布文件、用户后加功能和一键复色数据测试前后零意外变化。

浏览器验收覆盖审核节点、右侧栏、状态灯、受影响范围、重新执行选择、刷新恢复和长内容可读性。

## 16. 第一阶段完成条件

以下条件全部满足后才交给用户审核：

- 1.1–1.8 全部实现并有测试证据。
- 自动化测试和浏览器验收全部通过，没有已知错误。
- 完成至少一次“修改上游 → 精确影响传播 → 只重做受影响节点”的演练。
- 完成服务重启和新窗口恢复演练。
- 正式画布和一键复色无意外变化。
- 统一账本准确指向阶段 1 用户验收，不自动进入阶段 2 或阶段 4。
- 用户验收通过后，阶段 1 才标记 `accepted`。

## 17. 非目标

第一阶段不生成新的分镜、图片、旁白或视频，不调用付费模型，不重写现有画布，不迁移一键复色数据，不提前实现阶段 4–10 的业务功能。

## 18. 文档迁移

本设计经用户书面审核后：

1. 以 10 阶段路线替换旧任务总表中的 16 阶段路线。
2. 保留旧阶段编号到新阶段编号的映射，不抹去历史完成记录。
3. 更新开发进度的当前阶段为“新版阶段 1：执行底座与恢复账本”。
4. 创建 `execution-ledger.json`、恢复协议、决定日志和阶段映射。
5. 旧计划中与本设计冲突的内容标记为 superseded，不静默删除历史文档。
